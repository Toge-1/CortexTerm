01 / PURPOSE & MAP

这套记忆究竟解决什么问题？

你在一个会话里告诉 Agent：“Windows 下必须用 py -m pytest，直接运行 pytest 会选错解释器。”新开会话后，这句话不一定还在模型上下文中。Memory V2 要做的，是让 Agent 在需要时能找回这条约定及其来源。

过去发生了什么

保存用户问题、公开回复、工具调用和工具结果。即使没提炼出经验，仍然能查原文。

turns 历史表
哪些经验能复用

后台模型提炼结论、选择 scope 和原文片段；程序取得 quote、比较旧经验后写入。主 Agent 只查记忆，不再调用 remember。

memories 经验表
这次该用哪些

根据查询搜索历史或经验，返回少量片段。模型需要详细证据时再打开原记录。

memory_search / memory_read

它和现有 Session、compaction 的区别

模块回答的问题主要作用
Session 保存 / 恢复“我上次那个会话继续到哪里了？”恢复会话消息、界面展示、输入历史等状态。
Compaction“当前发给模型的上下文放不下了怎么办？”压缩当前工作上下文，保留近期消息。
Memory V2“以前的约定、失败经过或操作，哪里能找到？”跨会话存储公开证据，提供按问题检索和可选经验提取。

当前 V2 另外保存一份公开事件，并没有只在 Session 文件上建立索引，所以存在一定重复存储。旧 Session 不会自动全部导入；开启 V2 后才开始积累新历史。旧版显式记忆文件会做幂等导入，原文件保留。

02 / DEFAULT BEHAVIOR

直接启动，一套记忆功能。

cortexterm

启动后保存每轮公开历史，后台提取可复用经验；模型需要时调用 memory_search / memory_read。话题查询统一 BM25，纯时间查询按时间分页。不需要选择记忆版本，不自动把旧记忆塞进每轮 system prompt。

有模型配置且有预算时，后台会额外调用已配置的 API。提取与比较共用每进程默认 30 次调用预算；用完后保存待处理任务，下次继续。只需要调整费用时设置 memory.maxExtractionCalls；设为 0 暂停额外调用，留档和已有内容搜索仍可用。

旧 JSON 记忆自动幂等导入，原文件保留；旧 mode、autoExtract、autoRecall、graph 字段不再选择运行策略。数据库故障会报告，不静默切换回旧版全量注入。

源码：memory_v2/runtime.py::create_memory_manager。

03 / ONE EXAMPLE

先用四轮对话，把三种“记住”分开。

直接运行 cortexterm，后台整理默认启用，内容按需读取。下面的提取结果是说明性示例，不是模型必定输出的内容。

  1. 你说：“你好。”

    Agent 回复后，这一轮原文进入 turns。后台依然会领取它并发起提取请求。提示词要求没有可复用内容就返回空列表，因此预期不增加经验。原文被保存，经验可以是零条；提取调用已经发生。

  2. 你说：“这个项目在 Windows 下测试用 py -m pytest。”

    原文照常保存。后台可能提取经验“本项目 Windows 测试使用 py -m pytest”，选择 project 范围和来源片段 ID；程序取该片段原文供比较，通过后保存 active 记录。

  3. 新会话里你说：“按之前约定跑一下测试。”

    主模型可以调用 memory_search({"query":"Windows pytest 测试"})。工具找到经验，返回内容和 ID；模型需要核实再调用 memory_read，然后决定调用 run_command。没有任何规则保证主模型每次都主动查记忆。

  4. 你纠正：“同一个 Windows 项目现在改用 uv run pytest。”

    后台拿本轮历史与检索出的旧经验比较。如果旧记录被提供给模型，且新证据明确修正同一条件下的结论，模型可以返回旧 ID 的 supersedes 关系。程序校验后写新记录、使旧记录失效。如果旧记录没检索出来，就可能同时留下两条冲突经验。

只有后台这一条正常写入路径。

主 Agent 不再拥有 remember 工具。你说“记住这个”会作为本轮内容交给后台模型，和其他经验统一提取、去重及更新。

主 Agent 每次请求模型前都会收到本会话最近三轮的后台状态。ADD/SUPERSEDE 表示已提交，NOOP 指向已有记录；pending/running 尚未保存，failed 表示失败。不会把“想记住”冒充“已经记住”。

可复用性、范围和修正关系由后台模型判断；程序检查来源编号、作用域和版本。结构校验不能证明结论正确。

04 / CAPTURE

哪些话保存？什么时候真正写到硬盘？

当前没有“有价值才存原文”的过滤器。只要启动了 V2，并且一次输入实际进入 run_agent_turn()，这一轮收集到的公开消息就会尝试留档。打字尚未提交，以及没有进入 Agent Turn 的本地斜杠命令，不走这条记录流程。

内容原始历史是否记录是否应成为自动经验
“你好”“好的”进入 Agent Turn 就记录通常不应；由模型返回空经验列表。
明确的项目约定、长期偏好记录提示词鼓励提取，要求带证据。
“正在修改第 3 个文件”等进度公开消息会记录提示词要求排除临时进度。
工具调用参数、工具结果、报错记录公开内容，并做有限脱敏只有可复用的环境约束、方法或失败经验才应提取。
system、隐藏 thinking、压缩摘要不记录到这条 V2 原文流不会作为该流程的提取材料。
程序追加的 user-role 重试指令不作为真实用户消息录入避免把程序自生成指令学成用户偏好。

“一轮”不是“模型调用一次”。

你提交一次问题后，Agent 可能调用模型三次、执行五个工具。对于这个记录器，仍然是一次 run_agent_turn()。它在入口记录真实用户问题，随后记录内部新增的公开消息。

# 简化示意：展示生命周期，不是把所有细节复制过来
recorder = TurnRecorder(这次用户问题)
try:
    return 执行_agent_loop(记录器=recorder)
finally:
    memory_service.capture(recorder)  # 本轮结束时才尝试入库

原上下文装进 RecordedMessages 时不会重新录一遍。只有之后的 append() 才捕获新增事件。compaction 换掉消息列表后，会重新包上记录器，因此压缩不会让它丢掉已经收集的本轮原始事件。

历史编号和搜索结果的 source_ids，分别指什么？

原始 turns 表的 id 标识这一轮，每条事件的 id 标识其中一条原始消息。例如轮次 T42 包含消息 T42:0、T42:1。这些是原文自身的编号，作用是让程序能按地址找到这一轮或某条消息。

搜索时会把原文切成片段，给片段单独分配 ID，并在搜索结果的 source_ids 中放它所属的原始事件 ID。例如片段 T42#chunk:1:1600 的 source_ids 是 ["T42:1"]；模型拿 T42:1 调 memory_read，就能读完整的那条原消息。这里表达的是“片段来自哪条原文”，不是原始历史又根据更早信息提炼而来。

turns 数据库表本身没有 source_ids 列。如果把完整 turn 包装成统一的搜索 / 读取结果，其 source_ids 列出该轮包含的全部事件 ID；自动提取经验的同名字段则指支撑经验的那些原始事件。它们最终都指向原文事件，但所在记录的含义不同。

正在执行时

事件暂存在 recorder.events 这个内存列表里，每条分配 turn_id:序号 作为稳定事件 ID。

结束或 Python 异常退出时

finally 把整轮内容写入 turns，默认状态 pending。原文和待处理状态是同一条数据库记录。

边界：不是每条消息立即落盘。强制杀进程、断电等让 finally 没执行时，尚未入库的这一轮会丢失。数据库写入失败时，记录警告，主 Agent 的正常结果不因此被替换成记忆错误。当前也没有原文自动淘汰。

三条写入入口与审批

原文留档和后台提取不逐条弹审批。读工具通过 ToolContext.memory_service 访问同一个服务。后台处理结果在主模型请求前临时注入，计入预算，但不写入原始对话或再次提取。

源码：agent_loop.py::run_agent_turn / _refresh_runtime_memory_context；memory_v2/service.py::capture / feedback。

05 / EXTRACTION

后台什么时候整理？到底筛选了什么？

启动时，有模型配置和可用调用预算，就创建提取模型并启动 memory-extractor 线程。它逐个领取当前工作目录的待处理历史；每轮留档后会唤醒它，程序启动时也会处理遗留任务。

实际触发条件：有待处理历史 + 提取已开启 + 本进程还有调用额度。

没有等满十轮，没有等到原文超过某个大小，也没有先用规则判断这一轮是否值得花 API 费用。纯寒暄同样可能产生提取调用，返回空结果只是“没有新增经验”，不是“没有调用模型”。

模型收到哪些材料？

  1. 取一轮未处理的公开历史。

    先保留最初用户问题，再优先挑近期结果。单个字符串 content 截到 6,000 字符，序列化材料合计最多约 24,000 字符；挑完再恢复事件先后顺序。这个截断只影响提取输入，不会删数据库原文。

  2. 先提取候选。

    程序把材料划成最多 1,000 字符的片段，尽量在换行处切分，标记 ID 和位置。模型返回零到四条候选，同时选 scope 和 1–8 个依据片段 ID。程序检查 ID 存在，将候选保存到 turn_candidates；空候选直接完成。模型不抄原文、不算字符偏移。

  3. 再用候选找旧经验。

    用正文、关键词、实体查找旧记录。同一作用域的记录可替代；更宽范围的记录只供参考，各组取前八条。窄范围经验不能阻止新增宽范围约定。旧 remember 记录也可以在相同作用域被明确的新结论修正。

  4. 必要时第二次调用模型比较。

    精确重复直接去重，没有旧命中直接新增；否则同轮候选批量比较，返回 ADD、NOOP 或 SUPERSEDE。程序限制替代目标和版本，并用事务提交。使用当前 runtime 的模型，无工具；提取输出预算 2,400 tokens、比较 1,600 tokens，请求超时配置 45 秒。

“提取经验”不是把原文缩短一下

下面是提取模型返回格式的示例。模型选中程序预先编号的片段，程序从该位置取得 quote 交给比较模型：

{
  "memories": [{
    "kind": "environment",
    "statement": "本项目 Windows 环境运行测试使用 py -m pytest。",
    "keywords": ["Windows", "pytest", "测试", "test command"],
    "entities": ["测试环境"],
    "scope": "project",
    "evidence_ids": ["T42:0#part:0"],
    "supersedes": []
  }]
}
字段作用谁来确定 / 检查
statement下次可直接阅读的经验，要保留适用条件。模型生成。提示词要求每条 ≤900 字符；程序实际上限为 1,200 字符。
kind区分决策、方法、环境、失败、偏好。提示词约定这些类别；当前校验并未严格枚举所有 kind。
keywords / entities补充搜索词；实体也用于实验性关联。模型生成，程序检查列表类型并裁剪数量、长度。
scopeuser 跨项目偏好、project 仓库约定、local 当前目录及环境。模型依据材料选择，依据不明用 local；程序检查枚举和归属。
evidence_ids选择支撑结论的原文片段，可跨消息。程序校验编号，保存来源 ID 和片段位置；比较或读取时从原文生成 quote，不逐字校验模型输出。
supersedes第一阶段保持空数组，不直接选旧 ID。第二阶段用 SUPERSEDE + targets 表达替代，只能修改比较名单中同作用域的记录。

提示词要求排除秘密、通用建议、临时进度，保留失败和不确定性，不把助手自称成功当作验证。来源编号有效不代表模型选对了片段、scope 或结论。原文仍可回查；长消息的输入预算仍可能使部分内容未被提取模型看到。

费用与失败细节

运行时默认每进程最多 30 次记忆模型调用，由提取和比较共用；失败尝试也占额度。一轮正常处理一次提取、必要时一次比较。两阶段之间用尽预算则保存候选、放回 pending，不消耗失败次数；恢复时继续比较，不重新提取。这个限制不是月账单上限，也不是所有主 Agent 请求的上限；底层网络请求仍受 adapter 的请求策略影响。

对当前代码专门识别的 api.deepseek.com，提取请求默认关闭 thinking，避免输出预算用完却没返回 JSON；这不改变主编码 Agent 的思考设置，也没有对所有提供商套用同样规则。

源码：memory_v2/runtime.py::create_memory_manager；service.py::start / _work / process_one / _validate_proposal；model.py::extract / consolidate / complete。

06 / DEDUPLICATION & CORRECTION

重复不再加一条，修正也不直接抹掉过去。

这里没有实现一个能任意重新编排整座记忆库的“合并 Agent”。目前提供的是局部比较、精确去重、带出处的替代。

情况当前处理局限
同一 turn 再次入库turn ID 为主键，INSERT OR IGNORE 防止重复插入。不同 turn ID 即使内容一样，也分别保留历史。
候选陈述与提供的旧经验相同合并空白后精确比较，相同则 NOOP；原始新历史仍保留。精确去重检查可见有效旧记录及同批候选；改写措辞再由比较模型判断。不会把新出处自动追加到旧经验。
同轮多个观察可合并提示词要求模型组织成一条简洁经验。不是程序实现了普遍的语义合并。
同条件下明确纠正旧知识新记录保存；旧记录 status 改为 superseded；links 记录替代关系。旧经验没被召回，或模型没识别纠正，冲突可能遗留。
旧记录来自以前的 remember仍可检索；后台可在相同作用域依据新原文决定跳过或替代。不会因为换成后台写入就删除已有记忆；跨作用域不能替代。

旧记录 m1

“本项目 Windows 测试使用 py -m pytest。”

status: superseded
仍然保留原始内容和出处。

新记录 m2

“本项目 Windows 测试现在使用 uv run pytest。”

status: active
m2 —supersedes→ m1

后续正常经验搜索默认只选 active 记录；按 ID 仍可读旧记录。历史原文搜索可能搜到旧说法，因此结果提供时间，并提醒对照当前代码或新纠正。失效标记不是把旧话从所有历史中删掉。

更新时还检查旧记录版本：后台从数据库读到 m1 后，若另一个进程已经修改 m1，本次提交会失败并回滚，避免拿过时状态覆盖更新。

源码：service.py::_comparison_context / _validate_decisions / process_one；store.py::enqueue / apply。

07 / RETRIEVAL

memory_search 怎么查：明确是 BM25，不把“混合”当“语义”。

查询文字由主模型写在工具参数里。用户说“按之前方式跑测试”，主模型可能改写为 Windows pytest 测试。MemoryService 收到的就是工具参数中的 query，不会再额外调用一个模型改写查询或做重排。

第一步：按范围拿记录，准备候选文本

先从 SQLite 读取本工作目录原文和当前可见经验。默认排除已被替代的经验，排除未来时间记录；有文件哈希的经验还会检查文件是否变化。然后在 Python 中计算 BM25，没有调用 SQLite FTS，也没有预建持久化倒排索引。

原文每个事件切成最长 1,800 字符的片段，起点按 1,600 字符递增，因此相邻重叠 200 字符。这有助于命中长工具结果中间或末尾的信息；片段边界只服务搜索，不参与模型消息协议的工具配对。

第二步：拆词并评分

拆词规则

英文转小写；保留完整标识符，同时按 _ . / : - 拆部分；中文使用相邻两字组合。

Windows → windows
run_command → run_command / run / command
运行测试 → 运行 / 行测 / 测试

这是简单字面处理，不是模型理解句意。

BM25 给什么加分

查询词在候选中出现会得分；越稀有的查询词通常越有区分度。重复出现会加分但逐渐饱和，并按文本长度做校正，避免长日志只靠字多占优。

当前参数 k1=1.2、b=0.75。没有共同词项时得分为零，不进入这一组结果。

把查询改成 “自动化验证”，同样三个候选的返回列表是空的。虽然人能联想到 pytest，但这里没有共同词项，BM25 不会自动理解这种语义关联。模型生成的别名可能改善用词差异，不能保证覆盖所有问法。

第三步：所有候选一起排一次，原文重叠命中合并

历史片段、显式记忆、导入记忆和自动提取经验都参与搜索。每条经验构造一个“正文 + 关键词 + 实体”文本，每个原文片段构造一个文本，统一计算一次 BM25。取消 RRF，没有经验的第二次投票，也没有时间排名加分。

同一条消息的相邻片段，如果命中了同一个原文位置，合并成一个结果并保留最高 BM25 分。不同位置的事实不会因为同属一轮就被删掉。经验和其来源原文仍是不同结果，类型和出处明确标注，不声称完成语义去重。

话题结果的 score 就是 BM25 分数，不是概率或真实性评分；不同查询、不同候选库的分数不应直接比较。关键词别名只增加词项匹配机会，不保证任意语义问法都能搜到。

时间浏览示例与公式

“昨晚聊了什么”：query 为空，按时间列每轮用户问题；看某轮实际结果再 memory_read(turn_id)。“昨晚测试为什么失败”：query 填测试相关词，先限昨晚，再 BM25，字体记录不会因时间符合而被加进结果。

BM25 对每个查询词累计：IDF × tf × 2.2 / (tf + 1.2 × (0.25 + 0.75 × 文档长度 / 平均长度))；IDF = ln(1 + (N - df + 0.5) / (df + 0.5))。tf 是词频，df 是包含该词的候选数量。

旧 graph/embedder 参数不再参与检索；旧关系和向量表保留，不删除用户数据。正常搜索无额外模型请求。

源码：service.py::search / _browse_history / _collapse_overlaps；store.py::history_page；retrieval.py::tokenize / bm25 / excerpt / parse_time_range。

09 / SQLITE

SQLite 的价值是管理更新和并发，不是让搜索自动变强。

数据库默认位置：%USERPROFILE%\.cortexterm\memory-v2\memory.sqlite3。它是本地文件，使用 Python 标准库 sqlite3，不需要 Redis、独立数据库服务或新运行时依赖。启用 WAL 时运行期间可能出现同目录的 -wal、-shm 辅助文件。

表保存的内容为什么需要
turnsturn ID、项目 / 工作目录、session、时间、用户问题、events JSON、处理状态、租期、次数、错误。同一条记录既是历史原文，也是后台提取任务。不需要另建一份队列文件。
memories经验正文、关键词、实体、来源消息 ID 和片段位置、scope、origin、status、version、时间等。不重复保存 quote 文本，读取时根据位置从原文还原。
memory_outcomes每轮已提交的 ADD / NOOP / SUPERSEDE 结果。与记忆更新同一事务提交，供主 Agent 查看实际写入结果。
linkssource、target、kind；kind 包括 supersedes 和 related。追踪纠正关系；兼容保留的 related 关系不参与排名。
vectors兼容保留的旧向量数据。当前检索不读取或生成向量。
turn_candidates已校验的提取候选 JSON。第二阶段失败或预算耗尽时，恢复比较而非重新提取。

表内仍然用 JSON 存复杂字段。turns.events 是 json.dumps(events) 得到的字符串；关键词、片段位置和处理结果也用 JSON 编码。数据库负责组织多条记录的状态与关联。

关键场景：一条新经验替代旧经验

比较项JSON / JSONL 也能怎么做本次选择 SQLite 的理由
只存几十条记忆一个 JSON 很直接，临时文件加 replace 可以整体更新。这类需求不强迫使用数据库。
连续历史追加JSONL 很合适，不必重写整个文件。本次还要更新任务状态和经验关系，并不只是追加日志。
多条记录一起修改可以自己设计日志、重放、锁和恢复协议，或整体换文件。事务直接表达这组原子更新，少维护一套协议。
多个进程领取同一任务需要跨进程锁，锁住“读取状态 + 改状态”全过程。事务中领取任务，数据库负责写入互斥。
检索速度与语义JSON 读入后也可以计算同样 BM25。当前主要收益是存储管理；搜索仍在 Python 全量计算，不能宣称数据库已解决性能问题。

源码：memory_v2/store.py::connect / enqueue / claim / apply。每次数据库操作使用自己的连接；网络调用不放在数据库事务里面。WAL 支持读写更好地重叠，但仍不是多个写事务同时任意写入。

10 / JOB LIFECYCLE

后台失败了，会不会丢原文、重复处理或堵住 Agent？

一轮历史的 state 只表示“经验提取处理到哪一步”，不是这轮主 Agent 是否成功。主 Agent 修复失败的历史，也可以被成功整理成失败经验。

两阶段之间额度用尽：保存 turn_candidates，running 回 pending，不消耗失败次数。比较失败则 failed；人工重试时复用候选，重新检索旧经验。依据旧经验作 NOOP 的提交也检查旧记录版本，防止比较期间它已失效却丢掉新候选。

为什么需要租期和 attempts？

进程 A 领取任务后可能崩溃。如果永远保留 running，其他进程就永远不接手。所以领取时设置 180 秒租期，过期后允许重新领取。attempts 既限制领取次数，也用来识别这一轮任务的持有者。

A 领取任务：attempts = 1
A 太久没提交，租期到期
B 重新领取：attempts = 2
A 后来才拿到网络响应，尝试写结果
数据库检查：当前 attempts 是 2，A 只持有 1 → 拒绝 A 的提交

这样不会让“过期的旧线程”覆盖新线程的结果。但不保证网络请求恰好只调用一次：租期接手时，旧进程可能还活着，短时间可能有重复请求。它保证的是过期结果不能随意发布，不是 exactly-once 的外部 API 调用。

线程什么时候等待、什么时候退出？

线程连续处理能领取到的任务；没有任务时用 Event.wait(1) 等待，新历史用 set() 提醒它。这个等待最多 1 秒，会周期性醒来检查；不是一个持续无休止空转的 while。真正的队列仍在数据库中，事件只用作唤醒提示。

退出设置停止标记，最多等待记忆线程 1 秒，不无限等待慢 API。任务如果来不及提交，之后可以按租期恢复。SQLite 连接有 5 秒忙等待超时，数据库无法写入也会失败；“后台”不等于所有 I/O 一定零延迟。

源码：service.py::_work / process_one / close；store.py::claim / fail / retry_failed / apply。

11 / BOUNDARIES

哪些记录能查，时间和隐私又怎样处理？

范围当前定义例子
user当前操作系统用户数据库内可跨项目使用。解释代码时先讲调用链。
project按 Git common directory 标识项目；同一仓库的 worktree 可共享这类记忆。仓库统一的测试约定。
local同项目且同一个规范化后的工作目录。当前 checkout 或本地环境特有的经验。
原始 turns始终按 project + workspace 过滤。不同 worktree 不会仅因同仓库而互相读到原始对话。

后台模型根据原文选择 user/project/local，不确定时选 local。跨项目偏好、仓库约定、当前目录环境分别对应三种范围。以上是查询隔离，不是操作系统级加密或多租户身份认证；同一 OS 用户直接读数据库文件仍能访问其中内容。

模型理解时间含义，工具按明确范围执行

主 Agent 依据每次请求前更新的本地时间与时区理解用户的时间含义，然后向 memory_search 传入 start_time、end_time。例如查询“2026-10-20 晚上”时，可以传入 2026-10-20T18:00:00+08:00 到 2026-10-21T00:00:00+08:00。工具只校验参数并执行范围查询，不从文本自动猜日期；含糊的时间应先询问用户。没有额外的时间解析模型请求。

两个时间参数须同时提供、带时区且开始早于结束，采用左闭右开区间。query 可为空，表示只查这个范围内的记录。带关键词时先按时间过滤，再做一次 BM25；空查询仅按时间分页列原始对话，不混入经验，也不计算相关性分。

用于筛选的是 turn 开始记录的时间，不是从对话文字推理出的现实事件日期。一轮跨过午夜，仍按该 turn 的 recorded_at 归属。句子“去年我配置过这个”不会让这条今天的记录自动归入去年。语义解析由主模型完成，程序不保证它对每个复杂表达都理解正确；自动预检索仍只用关键词，时间范围由工具调用明确指定。

安全边界

代码会对常见密钥格式和 password、api_key 等字段做脱敏；提取提示词要求日志是数据，不能执行日志中的指令。提取模型没有工具，搜索结果也提醒历史可能过时。这些是有限防护，不是任意秘密检测或对提示词注入的完整防御。

默认后台整理会把选中的历史材料额外发给已配置的模型接口，受调用预算约束；但主 Agent 调用记忆工具后，返回片段仍会随下一次正常模型请求发送。两条路径都需要区分“本地存储”和“进入 API 请求”。

源码：service.py::project_identity / redact / redact_value；store.py::records / turns；retrieval.py::parse_time_range。

怎么启动、怎么看它真的做了什么？

以下命令在终端输入。/memory 才是在 CortexTerm 自己的输入框中输入。

cortexterm

无需额外参数。调整后台调用额度时，可在原 settings.json 内合并这一项，不要覆盖整个配置文件：

"memory": { "maxExtractionCalls": 30 }
观察方式看什么额外调用模型？
TUI 输入 /memory记录数量、队列状态、调用数量和数据库位置。否
诊断命令 status可见记录和 pending / running / done / failed 数量。否
诊断命令 search搜索结果、BM25 或 chronological 策略、时间范围、候选数或翻页游标、耗时。不调用模型
诊断命令 read按 ID 打开记录或原始证据。否
诊断命令 process主动处理积压提取任务，可选择重试失败任务。是
# 在项目目录中运行。前三个不做经验提取。
python -m cortexterm.memory_v2 status
python -m cortexterm.memory_v2 search "Windows pytest"
python -m cortexterm.memory_v2 read <搜索返回的ID>

# 这条会发出真实提取请求，最多处理 5 次
python -m cortexterm.memory_v2 process --max-calls 5 --retry-failed

# 指定项目时，全局参数写在子命令前
python -m cortexterm.memory_v2 --project D:\MiniCode\CortexTerm status

诊断 search 和 TUI 使用同一套搜索规则，无需传模式参数。直接运行诊断命令也不会先自动导入旧 Session。

从现象判断处理到哪一步

  • pending 增加，memories 没增加：可能没有模型配置、预算已用完或后台还在处理。
  • done 增加，经验仍没增加：可能模型返回空列表，或候选被精确去重。这不表示没有消耗提取请求。
  • failed 增加：检查 API / JSON / 片段编号 / scope / 版本校验等错误；原文仍可搜索。没有模型抄错引文导致的逐字符校验失败。
  • 数据库有记录，模型却不知道：默认没有自动预注入；模型需要调用搜索工具，且还可能因用词不匹配而搜不到。
  • 搜索有结果，回答仍错：召回相关材料和正确使用材料是两件事，还要看返回片段、时间、上下文及主模型后续行为。

14 / EVIDENCE

工程机制跑通了，但“修复更强”还没有被证明。

以下为代码基线对应的既有评测记录，本文编写没有重新发起模型实验。测试正确性和 Agent 效果分开看。

工程测试

357 passed，3 skipped。其中 30 项 memory-v2 检查覆盖存盘、隔离、出处、任务领取、租期恢复、失效线程不能覆盖结果等。

模型效果

构造任务上，历史信息有帮助；真实仓库小样本上，自动预注入未改善修复，甚至出现更差结果。

读完后应能回答的六个问题

  1. “你好”会不会入库？原文保存和经验保存为什么不是一回事？
  2. 一轮内部调用五次模型，会不会生成五个提取任务？
  3. 后台调用额度用完后，已有内容还能搜到吗？
  4. 查询与历史没有共享词项时，当前 BM25 会怎样？日期查询为何又可能查到？
  5. memory_search 返回后，是谁把结果追加进模型上下文？
  6. SQLite 解决的是哪些存储问题，哪些检索和模型质量问题仍没解决？
对照答案
  1. 进入 Agent Turn 就留原文；提取模型可以返回空经验列表。
  2. 不是。记录器以一次 run_agent_turn 为单位，结束时产生一条待处理历史。
  3. 可以；原文、显式记忆、旧版导入和已经生成的经验仍可查询，尚未处理任务留待以后。
  4. 话题搜索零命中就返回空。空 query 的日期浏览直接按时间分页列原始 turn，不做相关性排名。
  5. 工具返回 ToolResult，Agent Loop 追加对应 tool_result，下一次主模型请求带上它。
  6. 事务、并发领取、状态和关系更新；不自动解决语义匹配、经验真假、调用费用、全量搜索增长和磁盘淘汰。
